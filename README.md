# AstrBot 接入 dot：QQ MCP 插件（中文使用教程）

本仓库备份 **v0.3.2 实验版**：把已有 AstrBot 的 QQ 私聊、指定白名单群文字消息交给 dot，通过 MCP 工具读取和回复。它使用 AstrBot 已有的 `aiocqhttp` 平台，不替你登录 QQ，不调用 AstrBot 的默认大模型，也不需要新增桥接容器。

**请先看清当前状态：代码与合成测试已备份，但完整 AstrBot 加载、真实 QQ 收发、Tunnel 到 dot 的全链路，以及 Events 自动订阅仍未完成验收。工具能列出来、Tunnel 显示就绪，都不能证明 QQ 会自动回复。以下教程包含准备步骤和验收方法，不是“装完必定可用”的承诺。**

本文说明于 2026-10-14 核对；OpenAI 的按钮可能显示英文，因此在中文说明后保留必要的界面原文。你不需要阅读英文正文才能按本文准备。官方入口、权限和 Tunnel 操作以文末固定版本参考为依据；如果你的账户没有相关入口，不要凭空填写参数或购买无关 API 服务。

> 本次只更新仓库 README。代码、版本号和 `dist` 中的 v0.3.2 安装包保持原样，因此包内 README 仍是该备份当时的版本。使用教程以本页为准。

## 一、开始前需要什么

- 一套你已经能管理的 AstrBot；本版针对 **AstrBot 4.28.2** 的接口核对，不能保证所有新旧版本兼容。
- 已经正常登录并能接收消息的 **aiocqhttp QQ 平台**。`qq_official` 不在本版支持范围内。安装 AstrBot 和 QQ 适配器请按各自官方文档完成；本插件不能代替它们。
- **Linux x86_64 / amd64** 运行环境。本包只附带这个架构的官方 Tunnel runtime；ARM NAS 不应直接使用这个二进制。
- 能使用 OpenAI Platform Tunnel 的账户、组织及相应 ChatGPT 工作区权限。此功能是否对你的账户开放，以实际页面和管理员确认为准。
- 容器能够出站访问 OpenAI 服务，以及后续核验过的 Events 回调服务。使用内置 Tunnel 时，不需要把 8769 端口暴露到公网。
- 自己的 QQ 号、机器人登录的 QQ 号；两者要分清。群功能可等私聊验收通过后再开。

本插件本身不调用模型 API。“申请 API”在本文主要指申请 **Tunnel 运行密钥**，不是购买模型额度，也不是把其他服务的模型 API Key 填进来。本文不对账户资格、收费或地区可用性作保证。

## 二、先分清三种值

| 名称 | 哪里取得 | 填在哪里 |
| --- | --- | --- |
| Tunnel ID（隧道编号） | Platform 的隧道管理页面 | AstrBot 连接页面的 `Tunnel ID`，以及 ChatGPT 中选择的同一个 Tunnel |
| Runtime API key（运行密钥） | Platform 的运行 API 密钥页面 | AstrBot 连接页面的“替换运行密钥” |
| 本地 MCP 内部认证 | 插件首次明确启用/应用时自动建立，已有值继续保留 | 不用手动申请，也不用在本版页面复制或填写 |

另有 **Admin API key（管理密钥）**，只用于管理接口/命令行创建、列出、修改、删除隧道。本教程推荐网页创建隧道，**不要求你额外创建管理密钥，更不能把管理密钥当作长期运行密钥**。任何密钥都不要发到聊天、GitHub、截图或公开日志里。

## 三、申请权限并创建 Tunnel

### 3.1 检查组织和权限

1. 登录 [OpenAI Platform 的隧道管理页面](https://platform.openai.com/settings/organization/tunnels)。确认当前是你准备使用的组织。
2. 如果看不到 Tunnels，或页面提示没有权限，请先找组织/工作区管理员确认功能开放与权限；本插件无法解除这些限制。
3. 运行插件、使用连接器的身份，需要 **Tunnels → Read（读取）+ Use（使用）**。
4. 创建/编辑隧道的身份，需要 **Read（读取）+ Manage（管理）**；同一个人也要运行插件时，再具备 Use。
5. 管理员可在 [组织角色](https://platform.openai.com/settings/organization/people/roles) 中配置这些权限，再在 [组织群组](https://platform.openai.com/settings/organization/people/groups) 分配给正确成员。角色权限和密钥权限都要满足，不能只改其中一项。

官方权限依据：[Tunnel 权限、角色和群组说明](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/permissions.md)。

### 3.2 创建这个插件专用的 Tunnel

1. 在上面的隧道管理页，打开 **Create tunnel（创建隧道）**。
2. 给它起一个便于识别的名称，例如 `QQ-AstrBot`；说明可写“连接 AstrBot QQ MCP”。
3. 核对组织及工作区归属。需要在某个 ChatGPT 工作区里使用，就必须关联正确的工作区；仅在 Platform 创建成功，并不保证它会出现在那个工作区的下拉框。
4. 确认页面内容后创建，复制返回的完整 **Tunnel ID**。不要复制名称来代替 ID，不要自行补齐、删减或改写 ID。
5. 为 QQ 和微信使用不同的 Tunnel，避免两个不同 MCP 服务争抢同一个默认通道。

只有已具备管理密钥、需要脚本管理的进阶用户才考虑官方 CLI 的 `admin tunnels create` 路径。不要为了安装这个插件，把完整管理工具的命令强行套在包内的精简 runtime 上。

### 3.3 创建运行 API 密钥

1. 打开 [运行 API 密钥页面](https://platform.openai.com/settings/organization/api-keys)，确认组织与刚建的 Tunnel 一致。
2. 使用页面的创建密钥功能，取一个可识别的名称，例如 `QQ-AstrBot-runtime`。
3. 权限选择 **Restricted（受限）**，找到 **Tunnels**，只授予 **Read（读取）+ Use（使用）**。不要为省事选择 All（全部权限）。
4. 创建后按页面提示安全保存密钥。它只应由你输入自己的 AstrBot 管理页面；不要交给机器人、贴进 README，或写进公共仓库。
5. 若没有 Tunnels 权限选项，先核对组织、账户开放状态与角色，不要拿其他模型 Key 或 Admin Key 试错。

官方操作路径与密钥区分：[Tunnel 使用指南](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/end-user-guide.md)、[初次配置说明](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/onboarding.md)。

## 四、下载并安装插件

1. 先备份 AstrBot 现有配置及 `plugin_data`。备份可能含密钥和聊天内容，请保存在自己的受保护位置，不要上传本公开仓库。
2. 打开 [v0.3.2 安装包](dist/astrbot_plugin_dot_private_v0.3.2.zip)，使用 GitHub 的原始文件下载功能保存 ZIP；不要把 GitHub 仓库的“下载整个源码 ZIP”当作同一个安装包。
3. 可选校验：安装包 SHA-256 应为 `a1176bbe55e55967993b166b8ec384a850a7523039e95ba227b21f4df5e588e2`，同时见 [校验文件](dist/SHA256SUMS.txt)。这用于确认下载内容与备份一致，不代表已完成真实运行验收。
4. 在 AstrBot 插件管理中，通过从文件安装/上传 ZIP 的入口安装。已有同名插件时原位更新，**不要先卸载**；插件名仍为 `astrbot_plugin_dot_private`，用于延续旧配置和数据。
5. 初次安装先保持“启用插件”关闭。打开 AstrBot 侧栏的插件页面，找到本插件的“连接设置”。如页面没有出现，先检查版本与插件加载错误，不要换掉原有 QQ 平台。

本包已含官方 Linux amd64 `tunnel-client-runtime` v0.0.16，不需要另起微信 stdio 命令或下载一份不匹配的客户端。包内许可证和校验材料保留；来源签名未完成验证的部分见 [运行边界](TUNNEL_RUNTIME.md)。

## 五、填写 AstrBot 配置

### 5.1 基础配置

- **启用插件**：暂时关闭，待其他设置检查完成后再开。
- **我的 QQ**：填你自己的 QQ 号，私聊只接收这个账号。
- **群白名单**：先留空，私聊验证成功再逐项添加群号。
- **群回复模式**：保留“仅本人 @ 时回复”。“群内所有普通文字”会接收白名单群所有非机器人账号的普通文字，包括以后新加入的人，不能当成只允许你的小号。

### 5.2 连接页面：平台与本地 MCP

1. 选择现有的 `aiocqhttp` 平台实例。下拉框里的实例名可以是中文；平台实例 ID 不是机器人 QQ 号。
2. “机器人 QQ”填写当前平台实际登录的机器人账号，不能填“我的 QQ”。
3. 监听地址保留 `127.0.0.1`，端口默认 `8769`，MCP 路径为 `/mcp`。不需要把地址改为公网监听，也不用设置路由器端口转发。
4. **本地 MCP 认证自动管理**：首次明确启用/应用时生成，旧值复用。不要把 Tunnel 运行密钥当成本地 MCP 认证值。
5. **回调域名**先不要猜填。它是 Events 接收端实际提供并核验的 HTTPS 主机名，不是 Tunnel ID，不是 API 地址，也不是机器人网页。具体处理见第七节；为空会拒绝事件订阅，这是安全边界。

### 5.3 连接页面：Tunnel

1. 将第三节取得的完整 ID 填入 **Tunnel ID**。
2. 将运行密钥输入 **替换运行密钥**。已有正确密钥时留空会保留原值；字段不会回显已保存的秘密。
3. 打开 **启用 Tunnel**，保存高级设置。保存会停止旧连接，不会单凭保存就自动启动新连接。
4. 关闭基础配置的旧弹窗。随后重新打开基础配置，确认 QQ 与权限范围，再打开“启用插件”并保存；必要时在连接页面点击 **应用 / 重启**。
5. 基础启用仍关闭时，“应用”不会启动服务。不要同时编辑基础弹窗和连接页面，旧弹窗保存可能覆盖新的高级设置。

**注意：匹配到的 QQ 消息会被本插件截住，以避免默认模型重复回答。如果 dot/Events 尚未接通，可能表现为消息不再回复。准备工作可先做，正式切换前必须完成测试；失败时先关闭本插件，恢复原来的处理方式。**

### 5.4 网络需要代理时

连接页面可开启“启用代理”，地址格式为 `http://主机:端口`；例如 `http://192.0.2.10:7890` 只是保留示例地址，必须换成自己实际可达的代理。

- 只支持 HTTP CONNECT，不支持 SOCKS、`https://` 代理地址、地址内用户名密码、路径和查询参数。
- 代理认证在独立用户名/密码框输入。换代理地址需重新输入或明确清除旧认证，避免凭据送错服务器。
- 容器内 `127.0.0.1` 是容器自身；代理在 NAS 宿主机时，需要填写容器能够到达的宿主地址。
- 代理用于 Tunnel 和 Events；本地 MCP/健康检查直连。代理失败不会自动绕开代理改为直连。
- 回调域名仍需本地 DNS 解析及公网地址检查。此功能不等于远程 DNS 或任何网络限制的绕过方法。

更多边界见 [代理说明](PROXY.md)。不要公开代理账号和密码；界面的密码遮罩不意味着磁盘配置已加密。

## 六、在 ChatGPT / dot 中添加连接

1. 先检查 AstrBot 页面：本地 MCP 已启动，Tunnel 进程运行，健康/就绪检查没有失败。
2. 进入你要使用的同一个 ChatGPT 工作区，打开 [ChatGPT 插件页面](https://chatgpt.com/plugins)，点加号，选择 **Add custom MCP server（添加自定义 MCP 服务器）**。这是私人连接，不是把 QQ 服务提交到公共插件商店。
3. 在连接配置里选择 **Connection: Tunnel（连接方式：隧道）**，选择或粘贴第三节同一个 Tunnel ID。给连接起一个清晰名称，例如“QQ”。
4. 按页面配置匹配的认证方式，阅读风险提示，理解后选择继续，再点 **Create as a plugin（创建为插件）**。本版未实现 OAuth 登录；不要把 API 运行密钥填成 MCP 的 OAuth 凭据。创建后检查能否发现本插件工具：`qq_status`（查看状态）、`qq_read_message`（读取已捕获消息）、`qq_reply`（回复该消息）。不要创建一个指向容器 `127.0.0.1` 的公网 URL 连接来代替 Tunnel。
5. 本版由内置 Tunnel 给本地 MCP 添加认证头。不要另外配置一个不匹配的 `Authorization` 头来覆盖它；也不要为消除报错关闭服务端认证。
6. 找不到 Tunnel 时，逐项核对组织、工作区归属、使用者的 Read + Use 权限、本地 runtime 是否仍在运行，以及新 Tunnel 是否已完成传播。

官方参考：[当前 Secure MCP Tunnel 接入指南](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)、[连接器接入和认证转发说明](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/connectors.md)。本插件只是协议子集实现；若实际产品不接受其发现/认证方式，应停止在此步并记录脱敏错误，不能据此认定 QQ 接入已经完成。

## 七、Events 自动消息订阅：目前尚未完成验收

**“工具可调用”与“QQ 来消息会主动唤醒 dot”是两步。当前 v0.3.2 的真实 Events 订阅与自动回复仍待验证，不应承诺自动响应。**

本插件实现了 `events/list`、`events/subscribe` 和 `events/unsubscribe` 协议方法，但这不表示任意连接器界面都会自动完成订阅，也不表示这些方法就是聊天中可以直接调用的工具。

按 [官方 MCP Events 教程](https://developers.openai.com/plugins/build/mcp-events)，支持的入口包括 dot、网页 Work 聊天，以及桌面应用中选择 Cloud 的 Work 聊天。协议版本要求为 `2026-07-28`，还受工作区插件和事件任务权限限制。

实际接入需要这样验收：

1. 连接插件后检查是否发现 `qq.message` 事件。你可以对 dot 说明：“请订阅这个 QQ 插件的新消息；仅处理我已配置的账号和白名单范围。收到后先读取消息，测试阶段只通知我，不自动向 QQ 发送回复。”这是一条可修改的测试指令，不会因读到本文就自动执行。
2. 支持该协议的 ChatGPT 接收端会在 `events/subscribe` 请求中提供回调 URL 和签名 secret，普通用户不需要另行申请、编造或在聊天里粘贴 secret。
3. **本版还有手动域名白名单门槛**：维护者需要从实际订阅流程确认并核验回调的主机名，让用户将该主机填入“回调域名”后再重试订阅；不得回显签名 secret。若界面/错误信息无法安全提供准确域名，这一步仍是集成阻塞，不能靠猜测或放开所有域名解决。
4. 只填主机名，不含协议、端口、路径或通配符。例如真实 URL 若为 `https://callbacks.example.com/events`，应填 `callbacks.example.com`；这个域名只是例子，不是可用服务地址。
5. 确认签名 challenge 验证成功、订阅已保存；发送测试消息，检查 webhook 收到成功响应、dot 收到对应事件。测试结束要求停止订阅，并确认后续消息不再触发。
6. 只有上述链路确实通过，再明确规定自动回复范围和群隐私边界。不要用定时轮询或无关 webhook 冒充已经接通的 Events。

回调不能为空白名单就直接访问内网；HTTP、重定向、私网地址及不匹配域名会被拒绝。无法取得接收端实际参数或确认协议支持时，这一步就是未完成，应保持插件停用或只做受控手动测试。详见 [群回复规则](GROUP_REPLY_RULES.md)。

## 八、按顺序验收，失败就停在那一步

1. **原有 QQ 通道**：在启用本插件前，确认 AstrBot 能收到机器人账号的普通文字消息。
2. **本地服务**：启用后，确认平台绑定正确，MCP 服务与 Tunnel 进程启动；健康、就绪状态正常。`ready` 只说明本地准备状态。
3. **工具发现**：在连接器中看到上述三个工具，调用 `qq_status`。这还没有验证自动事件投递。
4. **消息读取**：用“我的 QQ”给机器人发一条无隐私测试文字，使用此次实际捕获的 `message_id` 读取。不要编造 ID，也不要填任意其他收件人。
5. **单次回复**：明确要求接收端回复这条测试消息，在 QQ 客户端亲眼确认是否收到且只收到一次。`adapter_completed` 仅说明适配器函数返回，不证明 QQ 已送达；`uncertain` 时不能换一个幂等键盲目重发。
6. **Events**：只有订阅验证与投递均成功、QQ 新消息确实触发 dot 后，才算自动消息通路成功。当前仓库尚不能勾选这项。
7. **群功能**：最后才添加一个测试群，确认白名单外、机器人自己、非授权账号/不符合所选 @ 条件的消息不被处理，确认没有重复回复。

本版只支持普通文字及允许的 @本机器人。图片、语音、文件、引用、转发、@其他人、@全体及混合组件不在支持范围内。不要把“不支持的内容没有回复”误判成 Tunnel 一定故障。

## 九、常见问题

| 现象 | 先检查什么 |
| --- | --- |
| 没有 Tunnel 页面或创建按钮 | 功能是否对账户开放、当前组织、管理员授予的 Manage 权限 |
| 运行认证失败/403 | 运行密钥与目标组织是否匹配、角色及密钥是否都有 Read + Use；不要替换成 Admin Key |
| Platform 有 Tunnel，ChatGPT 看不到 | 工作区关联、连接器使用权限、传播是否完成 |
| 显示本地就绪但 QQ 不回 | 工具发现、消息路由、Events 订阅；这些都不由 ready 自动保证 |
| 中文平台找不到 | 使用 v0.3.2，刷新平台列表，确认原平台为 aiocqhttp；不要因此改掉机器人名称 |
| ARM NAS 提示二进制不可用 | 当前包只带 amd64，不能把 amd64 文件复制成 arm64 文件名 |
| 代理启用后失败 | 容器可达性、HTTP CONNECT、认证、本地 DNS；不要关闭 TLS 或地址校验 |
| 保存后设置“变回去” | 是否使用了旧基础配置弹窗；关掉后重新打开再编辑 |
| 升级/重启后旧消息不能回复 | 原始事件句柄只保存在进程内；让发送者重新发一条消息，不要改路由或伪造 ID |

排查时只分享脱敏状态和固定错误码，不公开密钥、代理凭据、QQ 号、私聊内容或数据库。官方补充：[Tunnel 故障排查](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/troubleshooting.md)。

## 十、升级、隐私和验证边界

- 更新前备份配置和数据，保持插件关闭；上传同名 ZIP 原位更新，不卸载，不覆盖数据库。升级后按第八节重新验证。详见 [升级说明](UPGRADE.md)。
- 默认仅本人私聊。打开群白名单会处理群成员信息；“群内所有普通文字”扩大到白名单群所有非机器人发送者，请先确认群内预期及权限。
- 插件会在本机 SQLite 保存接收的消息、会话标识和投递/回复状态。同一个 MCP 认证客户端能够读取被接收的不同会话，**会话标签不等于记忆隔离**。群回复不能带入私聊、邮件或其他群信息。
- 关闭插件可停止后续处理；不能撤回已经交给适配器的网络发送。
- 清理运行数据前先确认保留与删除需求；本公开仓库没有任何实际配置、密钥或聊天数据库。
- 合成回归：224 个 Python 测试中 211 通过、13 跳过，另有 26 个 Node 测试通过。跳过项包含可选真实浏览器和 SDK 类型校验；不等于线上 QQ、AstrBot、Tunnel 已验收。详细范围见 [测试报告](TEST_REPORT.md)。
